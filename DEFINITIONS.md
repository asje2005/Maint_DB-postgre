# Manufacturing Operation Database — Definitions & Data Dictionary

**Version:** 2.2
**Last Updated:** June 2026

## Purpose

This document defines standard meanings, scopes, and rules for fields, identifiers, templates, and controlled vocabularies used in the Manufacturing Operation Database.

It exists to ensure consistent data entry, long-term maintainability, safe analytics expansion, and clear understanding for future contributors.

This document is authoritative. If a field or term is unclear, it must be clarified here before being implemented.

---

## 1. Core Identifier Definitions

### Asset_Code

**Example:** `L001`, `M002`

A human-readable identifier for a physical asset.

Structure: one letter indicating department/class + three-digit sequence number (001–999).

| Letter | Department |
|--------|------------|
| L | Lathe |
| M | Mill |
| S | Swiss |
| Q | Quality Control |
| E | Utility / Support |

Rules:
- Unique per physical asset
- Never reused
- Never changed once assigned
- The first letter must be one of `L` / `M` / `S` / `Q` / `E` — enforced by the Add Asset form (the `DEPARTMENT_CODES` list) and recommended as a `CHECK` at the database level

---

### Asset_ID

**Example:** `A-L001`

The canonical system identifier for an asset. Always equal to `A-<Asset_Code>`. Stored in the database and in all service records. Used for indexing and cross-reference.

---

### Service_ID

**Example:** `S-L001-20240410-001`

A unique identifier for a finalized service event.

Structure: `S-` prefix + Asset_Code + completion date (YYYYMMDD) + sequence number.

Rules:
- Generated by the system only
- Immutable once created
- Used only for finalized records

---

### Draft_Service_ID

In the current PostgreSQL system a Draft service record has no human-readable draft identifier. Drafts live in the `service_reports` table with `record_state = 'Draft'` and a NULL `service_id`; they are referenced internally by their `report_id`. A `service_id` (see Service_ID) is assigned only at finalization. The old `S-DRAFT-<Asset_Code>` Excel-file naming is no longer used.

---

## 2. Record State Definitions

### Draft

A mutable, work-in-progress service record that may be incomplete.

- Stored as a row in the `service_reports` table with `record_state = 'Draft'`
- Editable in the app's Edit Existing Draft page
- At most one open Draft per asset (enforced by the `uq_one_open_draft_per_asset` partial unique index)
- Not part of official maintenance history

### Final

A completed, verified, immutable service record.

- The same `service_reports` row with `record_state = 'Final'`, a generated `service_id`, and `finalized_at` set
- Treated as read-only by the app after finalization
- Represents an official historical fact

---

## 3. Asset Registry Definitions

### Asset Registry

The identity and static characteristics of a physical asset, stored as a row in the `assets` table in PostgreSQL.

- One row per asset, keyed by `asset_id` (e.g. `A-L001`)
- Asset identity data (manufacturer, model, serial, etc.) is created and edited directly in the app (Add Asset / Edit Asset pages)
- The original Excel registries were a one-time import source only (see `import_to_postgres.py`); they are no longer part of the running system

### Equipment_Category

High-level classification of equipment type.

Allowed values: `Lathe`, `Mill`, `Swiss`, `QC`, `Support`

### Primary_Function

The primary operational purpose of an asset. Stored as the free-text `primary_function` column on the `assets` table; the app collects it via a free text input, so there is no enforced controlled vocabulary. Common values include `Machining`, `Inspection`, `Handling`, and `Utility`.

---

## 4. Service Record Definitions

### Service Record

A row in the `service_reports` table representing a single maintenance event performed on an asset.

- One row per event
- Created initially as Draft (`record_state = 'Draft'`)
- Finalized in place (`record_state = 'Final'`, `service_id` and `finalized_at` set)
- Treated as read-only after finalization

### Service_Type

Why the service activity occurred.

Allowed values: `Preventive`, `Corrective`, `Emergency`

### Issue_Category

General domain of the issue encountered. Stored as the `issue_category` column on `service_reports` and chosen from a dropdown on the Edit Draft page.

Allowed values: `Mechanical`, `Electrical`, `Pneumatic`, `Hydraulic`, `Software`, `Operator / Process`, `Other`, `Unknown`

### Root_Cause

First-order classification of the identified cause. Stored as the `root_cause` column on `service_reports` and chosen from a dropdown on the Edit Draft page.

Allowed values: `Wear`, `Misalignment`, `Contamination`, `Electrical Fault`, `Software / Parameters`, `Installation Error`, `Damage`, `Unknown`

## 5. Parts and Battery Definitions

### Part_Used

A component, consumable, or item replaced or installed during a service event. Stored as a row in the `service_parts` table (one row per part), linked to its service record by `report_id`. Parts are added and removed on the Edit Draft page.

Each part row holds:
- `part_name` — required
- `quantity` — whole number, defaults to 1
- `is_battery` — see Is_Battery

### Is_Battery

The `is_battery` flag on a `service_parts` row, marking the part as a battery replacement (a checkbox in the app; stored as true/false). Used to identify battery replacement events for analytics.

### Battery_Replacement_Interval_Days

The expected replacement interval (in days) for an asset-installed battery.

- Stored in the `asset_batteries` table in PostgreSQL
- Represents expected lifecycle, not actual replacement date
- Actual replacement dates are determined from service records

---

## 6. Impact & Verification Definitions

### Downtime_Hours

Total production downtime attributable to a service event.

- Numeric; zero is allowed
- Required for finalized records

### Return_To_Service

Whether the asset was returned to operational status at the end of the service event.

Allowed values: `Yes`, `No`

### Verified_By

The individual who verified the completeness and accuracy of a finalized service record. Required for finalization.

## 7. System of Record

### Operational Data (PostgreSQL)

The PostgreSQL database (`maintdb`) is the authoritative source of truth for all operational data:

- Asset registry data (manufacturer, model, serial, location, batteries, peripheral equipment)
- Shop floor data (work centers, employees, jobs, labor tickets)
- All CRUD operations go through the app and are persisted in PostgreSQL

### Service Records

Finalized service records are rows in the `service_reports` table (`record_state = 'Final'`) with a generated `service_id` and a `finalized_at` timestamp. They are stored and read entirely in PostgreSQL — there are no longer any Excel files or `Service_Reports/` folders. The app treats finalized rows as immutable historical records.

### Upstream Sources (optional)

The PostgreSQL database remains the single source the app reads. Two optional upstreams can feed it:

- **JobBoss / ECI M1 sync** — pulls employees, jobs, and labor tickets from a JobBoss SQL Server
  *into* PostgreSQL (read-only against JobBoss, upsert-only into PostgreSQL; existing rows are
  updated, never deleted). Synced labor tickets carry their origin id in `labor_tickets.jobboss_ticket_id`
  so re-syncs are idempotent. Configured via `JOBBOSS_*` environment variables (no hardcoded
  credentials); run from **Advanced → Settings** or `sync_jobboss.py`. See `utils/jobboss.py`.
- **Legacy Excel service drafts** — the work-in-progress `S-DRAFT-<Asset_Code>.xlsx` files under
  `Maintenance_DB/_WIP/` are imported once into `service_reports` (as Draft rows) by
  `migrate_service_reports.py`; the running system uses `report_id` thereafter.

### Packaging note

The bundled desktop app ships and manages its **own** private PostgreSQL — the database, schema,
seed, migrations, and drafts are created automatically on first launch. The system-of-record rules
above are unchanged; only the database's location differs.

### Not the System of Record

- The UI (it reads from the DB)
- Indexes or dashboards (derived data)
- Draft service records (temporary)

## 8. Change Control

Any new field, vocabulary, or identifier must be:

- Defined in this document
- Added to `schema.sql` if it belongs in the database
- Reviewed for downstream impact on the app and any existing reports
- Versioned explicitly in this document
